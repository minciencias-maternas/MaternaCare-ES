# RAG benchmark operational telemetry

The benchmark JSONL keeps its existing fields and adds per-sample token, retrieval, timing, completion, and optional resource details. The summary retains its existing `operations` values and adds explicitly named `operations_mean` and `resource_metrics_mean_peak` sections.

## Per-sample JSONL

| Fields | Meaning |
|---|---|
| `input_tokens`, `output_tokens`, `total_tokens` | Integer counts for answer inference plus uncached HyDE work, as before. Existing `generation_latency_seconds` includes prompt preparation and model generation; `end_to_end_latency_seconds` remains retrieval plus generation. |
| `retrieved_chunk_count` | Number of ranked chunks returned. |
| `retrieved_context_characters`, `retrieved_context_utf8_bytes` | Sum across raw retrieved chunk texts, excluding separators, chat formatting, question, and system prompt. Bytes are UTF-8 encoded bytes. |
| `retrieved_context_tokens` | Sum of standalone tokenizer counts for each raw retrieved context, without special tokens. Null if the generator does not expose a compatible tokenizer method. This is distinct from full `input_tokens`, which includes formatted chat prompt. |
| `model_load_latency_seconds`, `hyde_model_load_latency_seconds` | One-time answer-generator or local HyDE generator factory/load duration, repeated on rows executed with that generator; neither is per-sample inference latency. Model loading itself is not included in the adjacent inference resource samples or energy integral. |
| `prompt_preparation_latency_seconds`, `model_generation_latency_seconds` | Local Hugging Face sub-stages. Prompt preparation covers chat formatting and tokenization; model generation covers `generate()` including CUDA synchronization. Null for providers that do not expose separable timings. These sub-stages are not a replacement for the existing end-to-end generation timer. |
| `retrieval_hit_at_k`, `retrieval_recall_at_k`, `retrieval_reciprocal_rank`, `retrieval_ndcg_at_k` | Diagnostics against the one supplied `reference_chunk_id`, at configured k. For one relevant item: hit/recall are 1 or 0; MRR is `1/rank`; binary nDCG is `1/log2(rank+1)`; misses are zero. Missing reference ID means null, not a miss. These are identifier-match diagnostics, not semantic relevance judgments. |
| `possible_truncation`, `completion_status` | The output count reaching configured `max_new_tokens` is flagged as `possible_truncation`; it does not prove the text was cut off. Successful rows otherwise use `completed`; a row-level execution/serialization failure uses `error`. Existing error and metric-error fields remain. |
| `process_*`, `system_*`, `cpu_*`, `gpu_*` resource fields | Interval-sampled statistics during answer inference. For uncached local Hugging Face HyDE, parallel per-sample details are nested in `hyde_resource_metrics`; HyDE cache hits have no current-run resource details. Each available sampled numeric metric has `_mean` and `_peak` fields. |

Resource sampling is best effort and does not fail the benchmark. `psutil` provides process CPU/RSS/thread count and system CPU/available RAM/core counts. CPU temperature is unavailable on Windows because psutil does not expose its sensor API there; no alternate temperature provider is used. CPU utilization baselines are discarded, and readings less than 0.1 seconds apart are unavailable; very short inference may therefore have RAM/thread readings but null CPU utilization. `nvidia-ml-py` (imported as `pynvml`) provides NVML utilization, memory, temperature, power, and SM clock (not memory clock) for a selected CUDA device. Mapping follows the pinned CUDA 2.5.0 visibility behavior without calling PyTorch's private `_get_nvml_device_index`: unset visibility requires a unique match on public CUDA device name plus total memory; numeric visibility entries map by their specified physical NVML ordinal; `GPU-` UUID visibility resolves against NVML UUIDs with a unique-match requirement. Unsupported, malformed, missing, duplicate, or ambiguous identities leave GPU values unavailable. Windows NVML loading uses NVIDIA's `NVSMI` and Windows `System32` DLL search directories when present; those search handles stay open through sampling and close after NVML shutdown. NVML requires a supported NVIDIA driver and the CUDA install path's `nvidia-ml-py` package; missing DLLs, initialization failures, and unsupported metrics degrade to unavailable values. Under Windows WDDM, memory readings may be system-wide and include a large baseline; GPU metrics are whole-device values, not attributable to this process. NVML power on Ampere and newer GPUs is a one-second average. CPU-only and unresolved/multi-GPU models do not sample an unrelated GPU. With a multi-GPU-sharded model, GPU readings and GPU energy are unavailable, while process/system CPU/RAM sampling can continue. A CPU+one-CUDA device map samples only that CUDA device and cannot separate CPU versus GPU work. Unavailable per-sample values are omitted and indicated by availability flags or null summary values, never fabricated zeroes. The default sampling interval is 0.5 seconds; disable sampling with `--telemetry-interval-seconds 0`.

The numeric and UUID visibility behavior was checked against the pinned [PyTorch v2.5.0 CUDA source](https://github.com/pytorch/pytorch/blob/v2.5.0/torch/cuda/__init__.py). Unset visibility instead uses a unique public-property identity match because an ordinal alone does not establish physical-device identity. Telemetry does not call PyTorch's private `_get_nvml_device_index`, whose UUID helper loads the Linux-only `libnvidia-ml.so.1` library. NVIDIA's [NVML API reference](https://docs.nvidia.com/deploy/nvml-api/nvml-api-reference.html) documents the Windows DLL search locations.

`psutil` is installed through the standard `requirements.txt` path. The CUDA requirements path also installs `nvidia-ml-py`; NVML remains optional at runtime and missing packages, drivers, or metrics do not fail a benchmark. The CPU-only requirements path provides process/system metrics without NVML.

```bash
pip install psutil nvidia-ml-py
```

## Summary JSON

- `operations` retains its existing keys and fractional means for backward compatibility.
- `operations_mean` repeats those existing operation metrics under explicit mean semantics and adds means for the new per-sample count, context, stage timing, retrieval-diagnostic fields, `gpu_energy_joules_estimate`, and `hyde_gpu_energy_joules_estimate`. Null values are excluded; an all-null field remains null. The energy means are across sample-level estimates, not total run energy.
- `resource_metrics_mean_peak` aggregates top-level answer-inference resource fields across per-sample rows as mean of sample means and maximum of per-sample peaks. It is not a time-weighted run-wide statistic; local HyDE resource details stay nested in each sample except for the explicit HyDE energy mean.
- `runtime` records Python/platform strings, selected library versions/provider installation, CUDA availability/device names when detectable, sampler interval, and HyDE provider. The existing `configuration` continues to hold model identifiers, generation settings, retrieval configuration, and revisions.

`gpu_energy_joules_estimate` is an approximate whole-device energy integral in joules for answer inference, computed from timestamped NVML power readings using trapezoidal integration. It is not process-attributed and excludes model loading, retrieval, evaluation, and idle periods outside the inference sample window. The estimate is null unless at least two readings have finite, non-negative power, strictly increasing monotonic timestamps, and at least one second of total coverage. This minimum avoids presenting a short fragment of Ampere+ one-second averaged NVML power as an estimate. The corresponding estimate for newly generated local HyDE work appears at `hyde_resource_metrics.gpu_energy_joules_estimate`; cached HyDE records never reuse historical samples as current-run energy. Sparse sampling, shared-device activity, and power-sensor limitations make both values approximate.

HyDE preparation runs before answer generation. Local Hugging Face HyDE cache misses are sampled per generated document, and their resource values and `hyde_model_load_latency_seconds` are recorded only for those uncached rows. The load duration measures generator construction once and is repeated for each generated record. HyDE cache hits have no current-run resource/load measurements; existing HyDE token/timing fields on such rows describe the cached generation and are marked by `hyde_cache_hit`, while combined operation totals exclude that historical work. OpenAI HyDE is remote request waiting, so it is not sampled as local hardware inference. If the local HyDE or answer model is sharded across multiple CUDA devices, no GPU index is selected; this version does not sum per-device readings. Existing HyDE cache rows that lack the new optional measurement fields continue to load.

The six existing RAGAS metrics and their error handling are unchanged. The current non-streaming generation timer is not time-to-first-token (TTFT).

- [ ] Run one short benchmark with default telemetry and confirm it completes even if individual NVML readings are unavailable.
- [ ] Confirm process/system resource fields appear, `cpu_temperature_celsius` remains unavailable, and unset, numeric-reordered, and UUID visibility each maps only to the matching physical GPU.
- [ ] On WDDM, interpret GPU memory as device/system-wide usage with its baseline; check that SM clock (not memory clock) is emitted.
